Tutoria 29/07/2026 — Banco de dados Oracle: views, índices, triggers e transações

Resumo didático — tutoria do curso 1 com o professor José Fernando (parte de banco de dados). Foi uma aula curta sobre conceitos adicionais de Oracle: estrutura do servidor (listener, instância, PDB), tablespaces, views, índices, triggers e transações. Também esclareceu o formato das avaliações.

O que foi coberto (cronológico)

O professor José Fernando abriu a tutoria explicando que cuida da parte de banco de dados do curso 1 (enquanto o professor Leandro cuida de Python). Fez uma apresentação sobre conceitos adicionais de bancos de dados no contexto do Oracle, o SGBD usado no curso (líder em bancos de dados corporativos — "a solução para quando você mexe com dinheiro").

Estrutura do Oracle usado no curso:

  • Listener (rcl-grad1.icmc.usp.br): serviço que ouve as requisições e direciona para a instância; não é o servidor em si.
  • Instância (ocrl-grad): caracterizada por memória e processos (uso exclusivo de memória).
  • Database físico: no caso, um PDB (Pluggable Database, via Oracle Container) — pdb-junior.icmc.usp.br. PDBs permitem portabilidade: dá para plugar/desplugar, fazer backup e cópia com facilidade.
  • Tablespace: a "superfície de disco" onde os dados ficam (arquivos .dbf). Organizado em segmentos, extents e blocks. O Oracle reserva o espaço na hora (ex.: 1000 MB) para gerenciar fragmentação e desempenho.
  • Esquema: cada usuário tem um esquema próprio, contendo objetos (tabelas, views, índices, procedures). O professor mostrou comandos de criação de usuário (create user), grant de permissões e atribuição de role (ele automatizou a criação dos usuários dos alunos a partir do CPF).

Conceitos adicionais (não essenciais, mas muito úteis):

  • View: consulta complexa "salva" com um nome (create view). Toda vez que é usada, a consulta é refeita (é como um alias). Usos: simplificar consultas, segurança (esconder nomes reais de atributos) e independência (se a base mudar, basta recriar a view — os softwares não quebram).
  • View materializada: o resultado da consulta é escrito em disco; não refaz a consulta a cada acesso. Ganho de desempenho em consultas pesadas (junções de várias tabelas), mas o conteúdo pode ficar desatualizado — exige política de atualização (manual, por tempo, ou refresh incremental).
  • Índice: cria uma árvore B sobre um atributo, reduzindo buscas de milhares de comparações para poucas leituras (ex.: achar "João Pedro" em ~3 leituras em vez de 5.000). Chaves primárias ganham índice automaticamente. Cuidado: índice não é de graça — escrita (insert/update) fica mais lenta, pois atualiza dados + índices; e não adianta criar índice em atributos com poucos valores distintos (ex.: gênero). Só vale para atributos com muitos valores diferentes e consultas frequentes (ex.: CPF).
  • Trigger: linguagem imperativa orientada a eventos do banco. Exemplo: atualizar automaticamente o número de alunos de uma turma após insert/delete/update em matrícula (atributo derivado). Usos: auditoria, segurança, automação, validação e consistência de dados.
  • Transações: a possibilidade de "desfazer" (Ctrl+Z) antes de efetivar. Exemplo: transferência de R$100 entre contas — begin → updates → commit (efetiva) ou rollback (desfaz). Enquanto não há commit, as alterações ficam no redo log e ninguém mais enxerga (nível de isolamento read committed, que evita "leitura suja"). O Oracle bloqueia linhas (não tabelas inteiras) para escrita; para leitura consistente usa snapshot (nível serializable), evitando leituras fantasmas.

Discussões e dúvidas da turma:

  • Formato das avaliações: avaliação final = 5 questões da quinzena 1 + 5 da quinzena 2, todas em formato de teste (sem escrita de código, mas podendo exigir analisar/escrever código). Avaliação quinzenal = 10 questões. Exercícios de fixação = escrita de código, criação de esquema e experimentos.
  • Avaliação quinzenal: dá para fazer aos poucos e enviar tudo de uma vez ao final (resposta do Elias, aluno).
  • View materializada vs view normal: esclarecida a diferença (consulta refeita vs resultado cacheado em disco).
  • Provocação sobre objetos complexos no banco: um aluno questionou se vale a pena ter views/triggers/procedures (acoplamento e dificuldade de migração entre tecnologias). O professor respondeu que o uso desses objetos é inevitável e exige engenharia de software clara (documentação, padronização, versionamento, "keep it simple"). Discutiu também o problema de incompatibilidade de fontes de dados (Excel, Postgres, Access) que leva a processos caros de ETL (tema do curso 3) e o papel da IA: ela acelera a escrita de código, mas a engenharia de software (requisitos, testes, deploy, segurança, conversa com o cliente) ainda é humana.
  • Transações e isolamento: esclarecido quem enxerga alterações antes do commit (apenas quem escreve, no read committed) e a diferença entre lock de linha e snapshot.

O professor encerrou recomendando: quem nunca trabalhou com banco de dados deve ver as aulas com atenção, fazer os exercícios e todos os laboratórios.

Pontos-chave / Decisões ou orientações

  • Oracle: listener → instância → PDB → tablespace → esquema do usuário. PDBs dão portabilidade ao banco.
  • View = consulta salva (refeita a cada uso); view materializada = resultado gravado em disco (desempenho, mas pode desatualizar).
  • Índice = árvore B para acelerar buscas; automático em chaves primárias; custa caro em escritas e não serve para atributos com poucos valores distintos.
  • Trigger = código imperativo do banco disparado por eventos (ex.: manter atributo derivado atualizado).
  • Transação = begin/commit/rollback; nível read committed evita leitura suja; Oracle bloqueia linhas (escrita) e usa snapshot (leitura) para isolamento.
  • Avaliação final: 5 questões por quinzena, formato teste; avaliação quinzenal: 10 questões, pode fazer aos poucos; exercícios de fixação: escrita de código.
  • Objetos complexos no banco são inevitáveis e exigem engenharia de software; IA acelera código, mas não substitui a engenharia.
  • Fazer exercícios de fixação e laboratórios é essencial para quem está começando em banco de dados.

Ações para o aluno

  • Assistir com atenção às aulas de banco de dados (Oracle) e fazer todos os laboratórios e exercícios de fixação.
  • Praticar no SQL Developer: create view, create index, create trigger, e os botões/comandos commit e rollback.
  • Explorar a estrutura do Oracle no ambiente do curso (listener, instância, PDB, tablespace, esquema).
  • Fazer a avaliação quinzenal aos poucos (dá para enviar tudo de uma vez ao final).
  • Revisar os conceitos de transações e níveis de isolamento (leitura suja, leitura fantasma, read committed, serializable).
